# Contributing to HIPIFY

We are enthusiastic about contributions to our code and documentation. Please
feel free to file issues where documentation or functionality is lacking or,
even better, volunteer to contribute to help close these gaps!

## Development workflows

### Issue tracking

Before filing a new issue, search through
[existing issues](https://github.com/ROCm/HIPIFY/issues) to avoid duplicates.

General guidelines:

- If your issue is already listed, upvote it and add a comment with reproduction details.
- When in doubt, file a new issue — we'll mark duplicates accordingly.
- Use the **Issue Report** form for bugs; for documentation or other non-bug topics, open a blank issue.
- Provide as much information as possible: the tool (`hipify-clang` or `hipify-perl`) and its version or commit, the full command line and output, the LLVM/Clang version `hipify-clang` was built with, the CUDA version, your OS, and a minimal CUDA source that reproduces the problem.
- Check your issue regularly — we may ask follow-up questions.

### Building

- `hipify-perl` is a standalone Perl script, [`bin/hipify-perl`](bin/hipify-perl), and needs no build. It is generated by `hipify-clang --perl`, so do not edit it by hand.
- `hipify-clang` is built with CMake against an installed LLVM/Clang development package, which CMake finds through `CMAKE_PREFIX_PATH`. Supported LLVM, CUDA, and cuDNN versions and the exact steps are in [build-hipify-clang-linux.rst](docs/building/build-hipify-clang-linux.rst) and [build-hipify-clang-windows.rst](docs/building/build-hipify-clang-windows.rst).

### Testing

- Regression tests are LLVM `lit` tests under [`tests/unit_tests/`](tests/unit_tests/): CUDA sources with a `// RUN:` line that runs `hipify-clang` and `// CHECK:` lines with the expected HIP output.
- To run them, configure with `-DHIPIFY_CLANG_TESTS=ON` and build the `test-hipify` target, for example `make test-hipify`. This needs Python 3, `lit`, `FileCheck`, and a CUDA Toolkit; cuDNN, cuTENSOR, CUB, cuFile, and cuSPARSELt are optional, set through the `CUDA_*_ROOT_DIR` options. `-DHIPIFY_CLANG_TESTS_ONLY=ON` runs the tests against an already built `hipify-clang`.
- Add or update tests for every mapping or behavior change, make sure existing tests still pass, and include the results in your PR.

### Changing CUDA-to-HIP mappings

Most changes add or update a mapping from a CUDA API to HIP (or ROC). Such a PR
usually changes these files together:

- `src/CUDA2HIP_<API>_API_functions.cpp` and/or `src/CUDA2HIP_<API>_API_types.cpp`: the mapping itself, including its version information.
- `bin/hipify-perl`: regenerated with `hipify-clang --perl`.
- `tests/unit_tests/synthetic/` (runtime and driver APIs) or `tests/unit_tests/synthetic/libraries/` (library APIs): new or updated `CHECK` lines.
- `docs/reference/tables/*.md`: regenerated with `hipify-clang --md --doc-format=full --doc-roc=joint` and `--doc-roc=separate` (see [README.md](README.md)); never edit these tables by hand.
- `src/Statistics.h` and `src/Statistics.cpp`: only when adding a newly supported CUDA, library, or HIP version.

### New feature or test development

Discussion about new features and test areas is welcome via:

- Filing a [GitHub issue](https://github.com/ROCm/HIPIFY/issues)
- Reaching out [on Discord](https://discord.com/invite/amd-dev)

### Pull Requests

All contributions should be submitted through a Pull Request (PR) against the
default branch, `amd-develop`.

Before submitting a PR:

- Title it `[HIPIFY][<tag>]...[<tag>] <summary>`, for example `[HIPIFY][fix] ...`, `[HIPIFY][doc] ...`, or `[HIPIFY][TheROC][BLAS][7.14][sync] ...`, and reference issues as `[#<number>]`.
- Fill in the pull request template (Motivation, Technical Details, Test Plan, Test Result).
- Keep the PR focused, and commit regenerated files (`bin/hipify-perl`, `docs/reference/tables/*.md`) together with the source change.
- Do not edit `CHANGELOG.md`; maintainers update it for each ROCm release.

PRs require:

- An approving review from a code owner of the changed files (see [.github/CODEOWNERS](.github/CODEOWNERS)).
- A squash or rebase merge: merge commits are blocked and `amd-*` branches keep a linear history.
- Green CI: the `Markdownlint mdl Action` (`build`) check and the `Security scan (PR)` workflow. Fix new security findings before merging, Critical and High first.

### Branching

- Do not commit directly to `amd-develop`; it is protected.
- Create a feature branch for all changes, in your fork or, with write access, in ROCm/HIPIFY.
- Keep changes focused and atomic.
- Update your branch by rebasing on `amd-develop` rather than merging it in.

### Commit Messages

- Use clear and descriptive commit messages.
- A squash merge uses the commit title for a single-commit PR and the PR title otherwise, so give single-commit PRs a commit title that follows the PR title convention.

### Code style

- C++ (`src/`): follow the style of the surrounding code; the repository has no `.clang-format`.
- CMake, Bash, GitHub Actions, and Python: follow the [ROCm/TheRock style guides](https://github.com/ROCm/TheRock/tree/main/docs/development/style_guides).
- Markdown: every push is linted by [markdownlint](https://github.com/markdownlint/markdownlint) (`mdl`) using [`.mdlrc`](.mdlrc) and [`mdlrc-style.rb`](mdlrc-style.rb); `README.md` is excluded.

### Documentation

Changes that impact functionality, configuration, APIs, or user workflows should
include corresponding documentation updates. The documentation sources are in
[`docs/`](docs/); see [README.md](README.md) to build them locally and
[Contribute to ROCm documentation](https://rocm.docs.amd.com/en/latest/contribute/contributing.html)
for the documentation contribution guidelines.

### Security Requirements

Contributors must not:

- Commit secrets, tokens, passwords, or credentials.
- Introduce vulnerable dependencies without justification.
- Bypass security controls or required security reviews.

All contributions are scanned automatically by the `Security scan (PR)` workflow
(CodeQL, gitleaks, zizmor, bandit, and Trivy).
